# Inbox→Evidence 정제 완료 후 공식 PII Scan 단계 부재로 Evidence가 Curation Queue에 무기한 pending

- Issue ID: `issue-20260803T011151Z-b35f5ac7`
- Recorded at: 2026-08-03T01:11:51.795444+00:00
- Reported by: kjkim
- Reported from: user
- Area: workflow
- Severity: medium
- Release observed: v1-c2f29370e7d6
- Status: open

## Summary

reconcile-inbox로 Inbox 8건을 Evidence로 변환했으나, ingest 단계의 정규식 기반 재검수(redact_sensitive_data)가 자격증명 등 고위험 패턴을 본문에서 마스킹하는 것과 별개로, 발행에 필요한 공식 Evidence PII Scan Receipt(RB-EVD-020, pii_scanned:true)는 inbox_reconciliation 계약(contracts/inbox.yaml)의 pending→accepted→evidence 단계 범위에 포함되어 있지 않다. Curation adapter도 비활성화 상태(config.yaml에 curation 섹션 없음)라 reconcile-curation으로도 다음 단계로 자동 진행되지 않아, 생성된 Evidence가 pii_scanned:false 상태로 Curation Queue에 계속 pending으로 남는다.

## Expected result

reconcile-inbox 완료 후 Evidence가 다음 단계(공식 PII Scan 또는 Curation)로 자연스럽게 이어지거나, 최소한 '공식 PII Scan 필요' 같은 다음 조치가 명시적으로 안내될 것

## Actual result

reconcile-inbox는 evidence 단계에서 종료되고, 결과 JSON의 sensitive_data_recheck는 카테고리(masked 여부)만 보고할 뿐 pii_scanned 필드는 항상 false로 남는다. record-inbox-pii-scan을 사람이 별도로 호출해야 하며, 이 필요성이 inbox_reconciliation 계약이나 reconcile-inbox 출력 어디에도 명시되지 않는다.

## Impact

Evidence가 발행(publish-changes) 불가 상태로 Curation Queue에 쌓이기만 하고, 사용자가 매번 개별적으로 상태를 질의해야 정체 여부를 알 수 있음. 축적될수록 정제 적체가 커짐.

## Reproduction or context

2026-08-01 python3 .circled-wiki/bin/circled-wiki.py reconcile-inbox --actor kjkim --limit 100 실행 → Evidence 8건 생성(knowledge/evidence/notion/2026/07/31/) → 전부 extensions.pii_scanned:false, pii_masked:false로 확인됨 → list-curation-queue에 8건 pending으로 계속 남음(2026-08-03 기준).

## Cause hypothesis

계약 설계상 Inbox 정제와 공식 PII Scan을 의도적으로 분리했을 가능성이 높으나(과거 이슈 issue-20260731T013303Z-9a1e688d에서 receipt 없이 pii_scanned:true를 잘못 기록한 사고가 있었던 것으로 보아, 안전을 위해 사람이 명시적으로 record-inbox-pii-scan을 호출하도록 강제하는 설계일 수 있음), 그렇다 해도 reconcile-inbox 완료 시점에 이 필요 조치가 CLI 출력이나 AGENT_BOOTSTRAP.md/AGENT_ROUTER.md에 명시되어 있지 않아 절차 모호성이 남는다.
