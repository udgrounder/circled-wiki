# RB-ROUTE-008의 propose_update 단계가 문서상 순서로만 존재해 실제로는 계속 스킵됨 — Gate로 강제하거나 CLI에 명시적 안내 필요

## Summary

OPERATING_RULES.md RB-ROUTE-008은 지식 변경 흐름을 'capture_* -> inspect_inbox -> review-data-protection -> accept_inbox -> ingest_accepted -> propose_update -> create_draft_bundle | apply_bundle_revision'로 명시하지만, propose_update 실행이 create-bundle/create-curation-review 실행의 전제조건으로 코드에서 강제되지 않는다. 이 설치본에서 Runtime Agent(Claude Code)가 2026-08-05~09 여러 세션에 걸쳐 이 단계를 한 번도 호출하지 않고 매번 grep으로 기존 Bundle 후보를 직접 찾아다녔는데도 create-bundle/promote-curation-candidate가 전혀 막히지 않고 정상 동작했다. curation-taxonomy.yaml 도입 이후 propose-update의 routing_hints·candidate_bundles·evidence_freshness가 실제로는 유용하게 동작하는데도(직접 테스트로 확인), 문서상 순서로만 존재해서 실제 운영에서 반복적으로 누락되는 구조적 위험이 있다.

## Expected result

propose_update 실행(또는 그 결과의 명시적 확인)이 create-bundle·create-curation-review·apply-automatic-curation-update 실행 전에 실제로 요구되어야 한다 — 예를 들어 create-bundle이 최근 propose-update 실행 결과(evidence checksum과 결합된 receipt)를 선택적으로 참조하도록 하거나, 최소한 knowledge-curation.md의 Checks에 'propose-update를 먼저 호출해 routing_hints·candidate_bundles를 확인했는가'를 명시적 항목으로 추가.

## Actual result

knowledge-curation.md와 OPERATING_RULES.md 어디에도 propose_update 미실행을 막거나 경고하는 Gate/Check가 없다. create-bundle CLI는 evidence_id만 있으면 propose-update 호출 여부와 무관하게 바로 Draft를 생성한다.

## Impact

중간 — Gate 위반은 아니라 데이터 무결성 문제는 없지만, taxonomy routing_hints·candidate_bundles 같은 유용한 기능이 반복적으로 사용되지 않아 Curator(Agent)의 판단 품질과 효율이 문서 의도보다 낮아짐. 특히 여러 세션에 걸쳐 반복된 것으로 보아 우연이 아니라 구조적 누락으로 보임.

## Reproduction or context

propose-update를 한 번도 호출하지 않은 상태에서 python3 .circled-wiki/bin/circled-wiki.py create-bundle --evidence <임의의 유효한 evidence_id> ... 를 실행하면 아무 경고 없이 성공한다.
