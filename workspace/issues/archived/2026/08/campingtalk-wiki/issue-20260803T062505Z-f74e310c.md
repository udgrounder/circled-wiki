# 자동 PII Scan이 Inbox 후보 checksum을 변경하면 inbox_reconciliation 작업 기록이 stale해져 reconcile-inbox가 반복 차단됨

- Recorded at: 2026-08-03T06:25:05.489080+00:00
- Reported by: kjkim
- Reported from: user
- Area: runtime
- Severity: medium
- Release observed: v1-cfe2e2235da7
- Status: triaged

## Summary

wiki upgrade(2026-08-03, run_automatic_pii_scan 도입)로 010 휴대폰번호 등을 감지하면 Inbox 후보 본문을 마스킹하고 checksum을 갱신하는데, 이 갱신이 workspace/task/inbox_reconciliation/<uuid>.md 작업 기록의 subject.source_checksum/source_checksum 필드에는 반영되지 않는다. 이미 sensitivity_review가 완료된 뒤 자동 PII Scan이 내용을 바꾸면, 다음 reconcile-inbox 호출이 has_blocking_inbox_review()의 checksum 비교(inbox_review_queue.py:66,129,142,229)에서 'active inbox review belongs to a different source checksum' 오류로 매번 차단된다.

## Expected result

sensitivity_review 완료 후 자동 PII Scan이 내용을 마스킹해 checksum이 바뀌어도, reconcile-inbox가 같은 작업 기록을 계속 사용해 정상적으로 Evidence까지 진행되어야 한다.

## Actual result

review-inbox-sensitivity로 completed 처리한 뒤 reconcile-inbox를 실행하면, 자동 PII Scan이 010 번호를 마스킹하며 Inbox 항목 checksum을 변경하고, 이후 재실행마다 동일한 오류로 accepted_count: 0, skipped_count: 2(reason: 'active inbox review belongs to a different source checksum')가 반복된다. workspace/task/inbox_reconciliation/<uuid>.md의 source_checksum을 현재 Inbox 항목 checksum으로 직접 수정해야만 다음 실행이 통과한다.

## Impact

sensitivity_review 완료 후 010 번호(또는 향후 추가될 자동 마스킹 대상)가 포함된 모든 Inbox 항목이 reconcile-inbox에서 무기한 반복 차단된다. 우회하려면 작업 기록 파일을 사람이 직접 patch해야 하는데, 이는 자동화 계약의 목적(사람 개입 없는 안전한 선행 단계 재수행)과 반대된다.

## Reproduction or context

## Resolution direction

Inbox Review Queue의 식별·연관·상태 재개는 `intake_id`의 UUID만 사용한다. 후보 checksum은 Queue 카드와
연관시키지 않고, PII Receipt가 실제 Evidence 후보 파일과 일치하는지와 후보 파일 변경 여부를 검증하는 데만 사용한다.
따라서 자동 PII Scan이 후보를 마스킹해 checksum을 갱신하면 기존 Receipt는 PII Scan 단계로 되돌리되, 같은 UUID의
Review Queue는 계속 사용한다.

## Cause hypothesis

기존 구현은 Inbox Review Queue를 `intake_id`와 `source_checksum`으로 함께 연관시켰다. 자동 PII Scan이 후보를
마스킹해 checksum을 갱신하면 Queue의 과거 checksum이 stale해져, UUID가 같은 작업도 재개하지 못했다. Queue 연관 키와
후보 무결성 검증 키의 책임이 혼합된 제품 결함이다.

## Review outcome

사용자 review와 product-defect triage가 완료됐다. 회귀 범위는 legacy Queue checksum이 남아 있는 상태에서 자동
PII 마스킹이 후보 checksum을 변경한 뒤 UUID 기준으로 재수용·Evidence 생성까지 진행되는 시나리오다.
