## Summary

dawn-curation.py의 04:00 'inbox 정제해줘' 요청이 tmux wiki 세션에 전송됐으나, 세션이 전날 저녁부터 미응답 상태였던 'curation 상태 확인해줘' 프롬프트 뒤에 그대로 남아 실행되지 않음. 09:00 리포트 확인 시점까지도 tmux 화면은 전날 저녁 상태 그대로였고 04:00~09:00 사이 git 커밋은 0건. 2026-08-05(로그인 만료), 2026-08-06(동일 증상)에 이은 3번째 재발이며, 2026-08-06 이슈(issue-20260810T000233Z-91857fff)와 동일 근본 원인으로 추정됨: 04:00 cron이 wiki 세션 상태를 '유휴 프롬프트'인지 확인하지 않고 무조건 send-keys를 실행함.

## Expected result

04:00 cron이 wiki tmux 세션에 'inbox 정제해줘'를 전송하면, 세션이 유휴 상태여야 하고 요청이 즉시 실행되어 Inbox가 정제되어야 함.

## Actual result

04:00 cron 로그(248edae062a0/2026-08-11_04-00-39.md)는 전송 시점에 이미 '⏵⏵ bypass permissions on' 대신 예상치 못한 상태를 감지했으나 그대로 전송을 강행함("예상치 못한 상태 — 요청 전송 시도"). tmux 세션은 실제로는 전날 저녁 미응답 프롬프트 'curation 상태 확인해줘' 위에 떠 있었고, 09:00 현재까지도 그 프롬프트가 그대로 남아있어 04:00 요청이 화면에 나타나지도 않음(입력 큐에 쌓였거나 유실). 05:00 dawn-check.py도 '새벽 시간대 커밋 없음'으로 실패를 감지했지만 09:00 일일 리포트 로직은 이를 성공으로 오인할 위험이 있음(과거 재발 시 확인된 패턴).

## Impact

3번째 재발로, 새벽 자동 Inbox 정제가 사실상 신뢰할 수 없는 상태. 실제 정제는 그날 낮 인터랙티브 세션에서 수동으로 이어받아 처리되고 있어 당장 데이터 유실은 없으나, 09:00 리포트가 새벽 정제 완료로 오인될 위험이 반복됨.

## Reproduction or context

저녁 인터랙티브 세션이 wiki tmux 세션을 미응답 프롬프트 상태로 남겨둔 채 종료 → 다음날 04:00 cron이 세션 상태 점검에서 '예상치 못한 상태'를 감지하고도 send-keys를 강행 → 요청이 큐잉되어 미실행.
